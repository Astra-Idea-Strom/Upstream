# SKILL-SELECTION.MD: Intelligent Skill Router & Graph Traversal Engine

> **Purpose**: Deterministic, token-efficient routing engine mapping colloquial human requests to the minimum sufficient set of specialized skills (typically 1 to 5 skills).  
> **Authority**: This document summarizes the deterministic routing logic implemented in `tools/route3.py` and specified in [`tools/skill-routing/SKILL.md`](tools/skill-routing/SKILL.md). Programmatic routing via `python tools/route3.py "<user request>" --paths` is authoritative.  
> **Mechanism**: Multi-ranker fusion (BM25 + phrase matching) over precomputed index shards (`index/cards/<category>.json`, `index/graph.json`, `index/bm25.json`) with intent gating and graph resolution.

---

## 1. The V3 Routing Architecture

The skill router prevents context bloat by never loading skill instructions upfront. It evaluates incoming tasks through a multi-tier pipeline:

```text
               USER REQUEST (Natural Language / Ambiguous)
                                  │
                                  ▼
                     STAGE 1: PROGRAMMATIC ROUTE
              - Invoke `python tools/route3.py "<user request>" --paths`
              - Zero-Manifest Runtime: loads Tier 0/1 shards, never raw manifest
              - Multi-ranker Reciprocal Rank Fusion (BM25 + exact phrases)
              - Hard negative-trigger vetoes and intent gates
              - Calibrated cut (0..N skills within token budget, max 5)
                                  │
                                  ▼
                    STAGE 2: GRAPH RESOLUTION
              - Resolves REQUIRES (mandatory dependencies from lead)
              - Resolves SPECIALIZES (child preempts generic parent)
              - Resolves ALTERNATIVE_TO (keeps superior option)
              - Enforces CONFLICTS (drops incompatible approaches)
                                  │
                                  ▼
                     MINIMUM SUFFICIENT SKILL SET
                    (Typically 1 to 5 focused skills)
                                  │
                                  ▼
                          STAGE 3: EXECUTION
              - Read ONLY the selected `SKILL.md` files
              - Load `references/` or `examples/` only when blocked
              - Re-route dynamically ONLY if new technical requirements emerge
```

---

## 2. Graph Relationship Semantics

Skills define edges to other nodes in the network, resolved automatically by `tools/route3.py`:

| Relationship | Implementation Status | Behavior | Example |
| :--- | :--- | :--- | :--- |
| **`REQUIRES`** | **Active (Enforced)** | Strict prerequisite. If Skill A is activated, Skill B is automatically included. | `threejs` -> `REQUIRES` -> `3d-web` |
| **`SPECIALIZES`** | **Active (Enforced)** | Specific child skill preempts generic parent when both match. | `postgresql` -> `SPECIALIZES` -> `sql` |
| **`ALTERNATIVE_TO`** | **Active (Enforced)** | Mutually exclusive alternatives; keeps the higher scoring candidate. | `nosql` -> `ALTERNATIVE_TO` -> `sql` |
| **`CONFLICTS`** | **Active (Enforced)** | Incompatible paradigms; automatically drops conflicting lower-scored skill. | Mutually exclusive frameworks |
| **`COMPLEMENTS`** | **Informational** | Recommended pairing for agent awareness. | `frontend-engineering` -> `COMPLEMENTS` -> `accessibility` |

## 3. Simultaneous Trigger Arbitration & Leading Skill Hierarchy

When a user request matches multiple skills simultaneously (e.g., *"fix this crash and make it not happen again"* matching both `core/debugging` and `core/error-handling`), the router applies deterministic arbitration:

### The Execution Phasing Protocol

Multi-skill workflows execute in structured phases determined by the router decision:

1. **Phase 1 (Lead Skill)**:
   - The primary objective with the highest confidence and priority (`lead`).
   - *Example*: `core/debugging` leads Phase 1 to isolate root cause and apply a surgical fix.

2. **Phase 2 (Supporting Skill)**:
   - Structural containment and resilience (`supporting`).
   - *Example*: `core/error-handling` activates to introduce error boundaries or retry backoff.

3. **Phase 3 (Verification Skill)**:
   - Automated regression testing (`required-by-lead` or supporting).
   - *Example*: `testing/unit-testing` confirms fix integrity without regression.

## 4. Operational Invariants

1. **Do Not Guess**: When multiple architectural paths are ambiguous, route via `tools/route3.py` or consult `tools/skill-routing/SKILL.md`.
2. **Minimal Activation**: Never activate more skills than needed to satisfy the acceptance criteria.
3. **No Legacy Manifests**: The system operates exclusively on index shards generated by `tools/build_index.py`.
